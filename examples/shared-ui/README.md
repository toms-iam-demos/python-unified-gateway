# Human-centered presentation baseline

Use the approved developer identity for the shared shell and technical workspaces. Business journeys retain their organization profile, plain-language decisions, readable evidence and clear next actions. Brand fidelity must never require inaccessible contrast, tiny text, hidden focus or controls that are difficult to reach.

`human.css` supplies reading sizes, focus treatment, comfortable controls, responsive navigation and reduced-motion/forced-color support. Load it after the host's styles. `human.js` improves native disclosure menus, Escape handling, section-link focus, sticky-navigation offsets and page titles. Load it after the page markup. It performs no network request and changes no authentication or provider behavior.

The shared workup renderer supplies its own typography and heading hierarchy. Native provider captures remain unchanged; provide adjacent controls and text explanations rather than rewriting evidence artwork.

Review live desktop and 320px layouts, 200% text/zoom, keyboard navigation, visible focus, form labels, table scrolling, contrast and reduced motion. Automated checks and visual review are evidence for those checks, not certification of a complete site. Screen-reader task testing and review with disabled users remain separate acceptance work.

The engineering target is WCAG 2.2 AA. Docusign's accessibility commitment does not establish the conformance of an embedded implementation or a site inspired by its Developer Center. See [the current accessibility hub](https://www.docusign.com/accessibility) and [the WCAG reference](https://www.w3.org/WAI/WCAG22/quickref/).

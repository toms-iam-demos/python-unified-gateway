# Enable HSTS on the live HTTPS gateway

Date: 2026-11-02 (America/Los_Angeles)

The maintainer explicitly requested activation. Added the Traefik `api-hsts` Headers middleware and placed `api-hsts@file` first on all ten HTTPS routers for the existing host. The live response is `Strict-Transport-Security: max-age=31536000`. Scope is this hostname only; child domains and browser preload enrollment are not enabled.

Traefik hot-reloaded the dynamic configuration. No container restart, image replacement, credential change, new provider call, authentication removal or route-target change occurred. Before mutation, semantic checks proved that only the middleware references changed; source hashes guarded against concurrent edits. Previous dynamic configuration was backed up privately on the server.

Live verification: home and health returned 200; catalog, documentation, classification, invitation admin and Stripe operator pages retained anonymous 401 responses; Stripe webhook GET retained 405; unknown HAM and gateway routes retained 404. All ten responses contained the exact HSTS header. Plain HTTP still returned 301 to the corresponding HTTPS URL. Traefik reported all ten HTTPS routers enabled with the middleware.

Recovery: restore the backed-up route configuration to remove the middleware attachment. Browsers that already cached HSTS retain it until its age expires; actively clear browser policy by serving `max-age=0` over valid HTTPS before removing the header. Retain valid HTTPS throughout recovery.

The reusable middleware definition is `deploy/traefik/api-hsts.yml`. Future route deployments must preserve its first position, including the visitor-cookie boundary and authentication-denied responses. This change supplies HSTS only; it does not claim MFA or a complete host security audit.
